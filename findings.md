## Material 3 Carousel Adoption Analysis
- The app currently uses Compose Material3 `1.5.0-alpha20`; the local dependency contains `androidx.compose.material3.carousel` with `HorizontalMultiBrowseCarousel`, `HorizontalUncontainedCarousel`, `HorizontalCenteredHeroCarousel`, `rememberCarouselState`, and `CarouselDefaults` APIs.
- Current UI has almost no real bitmap media. Most visual surfaces are icons, charts, QR codes, and widget previews, so carousel usage should be limited to visual summary/preview collections rather than operational lists.
- Best fit #1: Health metrics summary. `HealthMetricsSection` currently renders fixed-width 168dp stat cards in a horizontally scrolling `Row`. This matches an uncontained carousel if we keep text stable, or multi-browse if we want one emphasized metric plus peeked neighbors.
- Health filter chips should remain chips, not Carousel. They are controls, short labels, and need predictable tap targets rather than dynamic item masking/resizing.
- Best fit #2: Settings widget picker. The three `WidgetPickerCard`s are visual preview items with repeated structure, currently stacked vertically. A carousel could reduce vertical density and make preview comparison more natural, but it must offer a vertical "show all/add widgets" fallback or keep a list alternative for accessibility.
- Candidate fit #3: Health OCR/manual hero could become a hero carousel only if future content adds multiple rich visual entry cards (scan device display, manual entry, recent abnormal alert). Current single hero should remain a normal card.
- Candidate fit #4: Drugs category browsing could use carousel only for a short "featured/popular categories" strip above the grid. The existing full category grid is better for complete browsing and accessibility; filter `LazyRow` should not become Carousel.
- Candidate fit #5: Welcome onboarding already uses `HorizontalPager`. Replacing it with Carousel is not recommended because the pages are form/setup steps with toggles and permissions, not compact visual media items.
- Do not use Carousel for Home medication tasks, PRN, low-stock, interaction warnings, Health records, History calendar/logs, medication detail logs, or symptom diary entries; these are task/status records with substantial text/actions and need vertical scanability.
- Any carousel placed on a vertical page needs a non-horizontal way to access all items. Material recommends a Show all button or equivalent full vertical page/list; this affects Health metrics and Settings widgets if adopted.
- Implementation slice completed: Health metrics now use `HorizontalUncontainedCarousel`; Settings widget previews now use `HorizontalCenteredHeroCarousel`; filter chips remain outside carousel layouts.
- Added `CarouselAdoptionGuardTest` to prevent regression on those choices and to guard against converting Health/Drugs filter chips into carousel items.

## Dynamic Color And Color Role Audit
- Official Compose Material3 `ColorScheme` currently includes the expanded role set: surface container roles, surface bright/dim, scrim, surfaceTint, and fixed accent roles in addition to the older primary/secondary/tertiary/error/surface roles.
- `MedLogTheme` correctly uses Compose dynamic color APIs for the main Compose app path: `dynamicLightColorScheme(context)` / `dynamicDarkColorScheme(context)` on Android S+ when the user setting is enabled.
- The static fallback color scheme is incomplete for current Material3 APIs. `Theme.kt` only supplies the older core roles; `surfaceContainer*`, `surfaceBright`, `surfaceDim`, `surfaceTint`, `scrim`, `primaryFixed*`, `secondaryFixed*`, and `tertiaryFixed*` are left to Material defaults rather than a generated MedLog fallback palette.
- `Color.kt` likewise only declares the older core roles plus one static `calendarWarning`. It does not contain a complete light/dark Material3 role table.
- The XML activity theme is `android:Theme.Material.Light.NoActionBar`, not a Material3 base theme. This is mostly masked by Compose `MaterialTheme`, but non-Compose theme consumers and Android framework surfaces do not get Material3 dynamic overlays from XML/MDC.
- Notification tinting uses static launcher color resources instead of dynamic/theme roles. This is outside Compose `MaterialTheme` and will not follow wallpaper dynamic color.
- Glance widgets use `GlanceTheme` defaults and app color roles, but there is no project-owned dynamic/static color provider wired from the same MedLog palette/user setting. Treat widget dynamic color support as not fully audited/guaranteed.
- Most Compose UI code uses `MaterialTheme.colorScheme` roles and many container/on-container pairs correctly, but there are custom cases that can break role guarantees: static `calendarWarning`, `android.graphics.Color.GRAY` chart labels, black scrim in `ViewfinderOverlay`, and semi-transparent copies of role colors used as ad hoc containers.
- Health stat cards show a representative pairing issue: cards use `errorContainer`/`secondaryContainer` backgrounds but some supporting text and accents use `onSurfaceVariant`, `error`, `secondary`, or alpha-modified custom surfaces instead of consistently staying within the paired `onErrorContainer` / `onSecondaryContainer` role set.
- Optimization slice completed the main actionable gaps from this audit: static Compose fallback now explicitly supplies the expanded M3 role table, the reusable `MedLogLightColorScheme` / `MedLogDarkColorScheme` is available outside the app theme, notification tinting resolves from Material primary roles, and Glance widgets use a project-owned `ColorProviders` bridge.
- Custom hardcoded/ad hoc colors removed in the audited hotspots: `calendarWarning` was replaced by secondary/secondaryContainer roles, Health chart labels use `onSurfaceVariant`, and the QR/OCR viewfinder overlay uses `scrim`.
- XML remains a framework splash/post-splash theme rather than an MDC `Theme.Material3` theme because this project is Compose Material3-only and does not depend on MDC-Android styles. Non-Compose color-role consumers are now handled directly where they exist: notifications and Glance widgets.

## Material Motion And Shape Check
- MedLog is a Compose Material3 app, not an MDC Views app. Android View APIs from the provided checklist (`MotionUtils`, `MaterialContainerTransform`, `MaterialSharedAxis`, `MaterialFadeThrough`, `MaterialFade`, `MaterialShapeDrawable`, XML `shapeAppearance`) are not used by the main UI and are not required for Compose navigation/content animations.
- Compose motion is already centralized at the theme layer with `MotionScheme.expressive()`. Custom motion should continue to use `MaterialTheme.motionScheme` spatial specs for movement/size and effects specs for alpha/color.
- The audit found remaining unthemed default Compose transition specs in Welcome, Drugs, and Home task group expansion: bare `fadeIn()`, `fadeOut()`, `expandVertically()`, and `shrinkVertically()`. These have been replaced with `motionScheme` specs.
- `MotionSystemGuardTest` now scans all main Kotlin sources for legacy fixed durations/springs and parameterless transition specs so new custom animations stay tokenized.
- Compose shape theming is centralized through `MedLogShapes`, but its previous values were an expressive custom scale (`8/12/16/24/28`) rather than the Material 3 role values from the provided shape checklist.
- `MedLogShapes` now follows the Material 3 role scale available in Compose `Shapes`: extraSmall `4dp`, small `8dp`, medium `12dp`, large `16dp`, extraLarge `28dp`.
- The app still has component-level `RoundedCornerShape(...)` overrides. In Compose these act like per-component shape overrides; they are not inherently wrong, but a future full shape pass could replace repeated overrides with semantic helper shapes if the product wants stricter theme-only shape governance.

## Editorial Treatment Adoption
- Editorial treatments should remain standalone showcase moments driven by type, not a styling replacement for labels, navigation, list rows, chips, or routine form surfaces.
- Best MedLog fit: Home's today-progress card. It celebrates user progress/completion, already has animated state, and can carry a product-wide hero moment without harming task scanability.
- Poor fits in the current app: medication task rows, history logs, health records, settings rows, filter chips, and widget cards. Those are functional/scannable surfaces where large editorial type would reduce clarity.
- Implementation uses dedicated theme tokens (`EditorialTypography`) rather than ad hoc large `TextStyle` calls. This keeps similar future moments consistent and matches the guidance to create tokens for recurring editorial treatments.
- The first editorial moment is `EditorialProgressMoment`: a large animated progress numeral while in progress and a localized completion word when all planned doses are done. It uses existing motionScheme spatial/effects specs and Material color roles.

## External Seven-Segment Dataset Acquisition
- Repository data conventions: generated recognition data lives under `seven_segment_ocr/dataset/`, YOLO display detection data lives under `seven_segment_ocr/detection_data/`, and Kaggle domain adaptation expects real LCD data in a simple `images/` plus `labels.csv` layout.
- External sources should be staged separately under `seven_segment_ocr/external_datasets/` to avoid mixing third-party/raw files with generated training data and exported model artifacts.
- Initial priority order for automated acquisition: Kaggle medical/device datasets, Hugging Face `MiXaiLL76/7SEG_OCR`, Kaggle YOLO seven-segment data, Roboflow datasets if an API key is available, then YUVA/Oxford/PACMAN resources if direct public links can be resolved.
- Completed available downloads using Kaggle API plus aria2 RPC for speed and Hugging Face direct LFS/parquet download. Raw size is about 1.1 GB; extracted size about 900 MB; preprocessed size about 200 MB.
- `kaggle_bp_monitor`: 176 JPEG images and 176 Pascal/VOC XML annotations. The annotation class is `bp_monitor`; it marks whole-device bbox only and does not contain transcribed SYS/DIA/PUL readings.
- `kaggle_oximeter`: 98 JPEG images and 98 Pascal/VOC XML annotations. The annotation class is `oximeter`; it marks whole-device bbox only and does not contain SpO2/PR reading text.
- `kaggle_seven_segment_yolov5`: 1,657 YOLO images/labels, split as train 1,452 / valid 135 / test 70. Its class list is `0,1,2,3,4,5,6,66,7,8,9`; class `66` looks suspicious and should be audited before training.
- `hf_7seg_ocr`: 3,333 synthetic PNG sequence-recognition samples converted from parquet to `images/` plus `labels.csv`; labels use characters `-.0123456789`.
- Roboflow sources were not downloaded in this environment because `ROBOFLOW_API_KEY` is absent and Universe pages returned Cloudflare challenges. The Kaggle YOLO source itself appears to be a Roboflow export and partially covers the generic YOLO pretraining need.
- YUVA EB/Mendeley metadata is publicly visible and says 169 energy meter images under CC0, but file list/download API was not reachable without interactive JS/API access in this run.
- Finnegan/Oxford and PACMAN remain paper/reference resources for now; no stable direct public dataset/code download endpoint was resolved during this pass.
- Ground-truth audit: Kaggle BP Monitor XML has 176 `bp_monitor` objects with Pascal/VOC bboxes plus `rotation=0.0`; it has no screen bbox, no digit bbox, and no SYS/DIA/PUL text transcription.
- Ground-truth audit: Kaggle Oximeter XML has 98 `oximeter` objects with Pascal/VOC bboxes plus `rotation=0.0`; it has no screen bbox, no digit bbox, and no SpO2/PR text transcription.
- Ground-truth audit: Kaggle seven-segment YOLOv5 has valid YOLO bbox labels for all 1,657 images. It is digit/object detection ground truth, not sequence text ground truth. Label counts by class name are `0:983`, `1:1538`, `2:1133`, `3:979`, `4:836`, `5:836`, `6:800`, `66:3`, `7:606`, `8:713`, `9:531`; the rare `66` class needs manual review.
- Ground-truth audit: HF `7SEG_OCR` has 3,333 image-to-text rows with labels over `-.0123456789`; it is OCR sequence ground truth, but synthetic and includes odd strings such as `.-3820` and trailing-dot values like `5284.`, so label normalization policy should be explicit before training/evaluation.

## Unified OCR Pipeline Design
- A Kaggle-compatible PySide6 pipeline must keep the GUI separate from training logic. Core tasks should be headless modules or subprocess adapters; PySide6 observes `events.jsonl` and artifacts.
- Existing scripts already partially fit this model: `train_fastvit_ctc.py` and `kaggle_domain_adaptation.py` emit per-epoch JSON rows; `run_candidate_evaluation.py` writes unified evaluation JSON. Legacy `train.py` and detection generation need structured event adapters.
- The shared contract should be a YAML/JSON task spec plus JSONL event stream. Kaggle kernels consume the JSON task spec; PySide6 edits/runs the same spec locally and visualizes the same outputs.
- Required visual surfaces: dataset inspection previews/distributions, training curves/error examples/checkpoints, inference overlays, evaluation comparison tables, and Kaggle push/status/fetch artifact management.
- Kaggle packager should generate script-only kernels and never import PySide6. It should copy the needed OCR modules, `pipeline_task.json`, and `kernel-metadata.json`, then write outputs under `/kaggle/working/<run_name>/`.
- Implementation result: the headless core now lives in `seven_segment_ocr/pipeline/`, while PySide6 lives only in `seven_segment_ocr/pipeline_ui/`. Static tests verify the core does not mention `PySide6`, and the generated Kaggle entry script is also free of PySide6 imports.
- The example task must use the actual staged HF path shape: dataset root `external_datasets`, labels `preprocessed/hf_7seg_ocr/labels.csv`, image column `image_path`, and label column `text`. The preprocessed rows store image paths like `preprocessed/hf_7seg_ocr/images/000000.png`.
- Smoke inspect results now confirm available counts from the staged data: HF image-text `3333`, BP VOC image count `176`, and seven-segment YOLO image count `1657`. YOLO class `66` is emitted as a warning event instead of being silently relabeled.
- PySide6 via conda caused slow/noisy pixi environment changes in this workspace. The working setup uses pixi `[pypi-dependencies]` for `pyside6`, plus explicit Qt plugin path environment defaults in `pipeline_ui.app` so `QApplication` can find `libqcocoa`/`libqoffscreen` from the wheel.
